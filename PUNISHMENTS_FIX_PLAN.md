# Punishments production recovery plan

Follow the [phased implementation plan](PUNISHMENTS_IMPLEMENTATION_PLAN.md) for branch names, dependencies, and acceptance checks. This document records the incident findings and feature requirements.

## Why the punishment queue is unavailable

The production cutover stopped before activation. On November 23, 2026 IST, the public site's deployed bundle matched the Supabase project checked below. GitHub `main` was at `3c0d55a`, and production Supabase contained the member and live-role moderator punishment RPCs, the November seed, and the checked visibility function.

| Production check | Observed result |
| --- | --- |
| `punishment_rollout.activated_at` | `NULL` |
| `punishment_rollout.screens_visible` | `false` |
| Task rows, task action rows, November pass archive rows | `0`, `0`, `0` |
| One-minute Supabase schedule | Active. Four recent dispatcher-shaped responses returned HTTP 200, `success: true`, and zero reported errors. |
| Full November preview via the service-role Data API | HTTP 500, SQLSTATE `57014`. The query was canceled. The operator SQL path still needs timing and verification. |

The moderator queue and member API share the visibility gate in [the task API migration](supabase/migrations/20261123_punishment_task_apis.sql). The active Owner can open the Mod Panel, but the queue RPC returns HTTP 503 while the gate is closed. The ledger migration routes strike writes through the legacy writer until activation. That writer can still record dated strikes and caps the legacy count at three. It creates no punishment tasks. A successful dispatcher request therefore does not establish that the punishment ledger is active.

## Members with three strikes and no task

A read-only SQL tally matched valid November cycle dates, `strike` records, and effective dated additions against the displayed counters. All 15 profiles in the snapshot were active. The tally found 27 dated nightly strikes and zero effective dated additions. The existing records support **seven missing tasks** before any evidence review changes the ledger. The tally determines eligibility counts. The canonical preview still needs to supply deadlines, exact expected status, and pass balances.

| Displayed November strikes | Dated strikes | Profiles | Expected tasks |
| ---: | ---: | ---: | ---: |
| 3 | 3 | 6 | 6 |
| 2 | 3 | 1 | 1 |
| 2 | 1 | 1 | 0 |
| 0–2 | Matches the displayed count | 7 | 0 |

The two mismatches need a dated review. The three-source member qualifies if those records stand. The one-source member needs two additional verified cycles to qualify. Inspect check-ins, sleep logs, Metastrike replacements, prior corrections, and any dated operator evidence for the specific cycles. The inactive legacy cap can suppress writes after strike three. Review only cases with dated evidence that a strike should have been recorded, especially for members who reached that cap. A counter, a candidate dry run, or an absence of a sleep row alone cannot establish an eligible strike.

## 3. Add strike history to the My Sleep calendar

The [sleep-history route](src/app/api/members/sleep-history/route.ts) currently folds a nightly strike into the `missed` sleep status. The calendar therefore groups confirmed strikes with missed or late sleep, and the day inspector has no issuance timestamp or correction history. Show accountability alongside the existing sleep details in [SleepCalendarModal.tsx](src/components/SleepCalendarModal.tsx).

1. **Make strike days easy to find.** In the member's own **Profile → My Sleep → Calendar**, add a labeled strike marker on each affected sleep-cycle date. A late or missed check-in stays a sleep status. Use a separate marker for a recorded strike, and make it readable without relying on color. Provide a **Strike history** list for the displayed month, newest first, with each entry opening the relevant day. Members can browse prior months after progress rolls over.
2. **Show what happened and when.** The day inspector shows the sleep-cycle date that the strike counts toward, its recorded issuance date and time, the source such as missed check-in or staff correction, and whether it still counts. Show the Metastrike replacement deadline when it applies. Keep a replaced or removed strike in the history with its change timestamp and updated status. A proactive Metastrike appears as a pass that prevented a strike. Show multiple recorded events for a day in order. Use the stored cycle date for the calendar and Luxon for timestamps, with a visible timezone label. For example, a November 30 sleep cycle issued after midnight can appear under November 30 with a December 1 issuance timestamp.
3. **Use the same evidence as the ledger.** Add a session-authorized monthly strike history read under `/api/members/strikes`, using the signed-in active Discord-linked profile. Return dated events and their current counting status with private no-store caching. Keep the existing shared sleep-history response separate from the new timestamps, reasons and correction details. Reuse `nightly_strike_logs` and `strike_moderator_corrections` for dated sources and `verified_monthly_strikes()` for eligibility. Expose only member-facing status and reasons. Keep staff identities, internal notes and raw evidence private.
4. **Preserve issuance history through changes.** Record the original issuance time durably when an automatic strike is written, and preserve the previous state when a strike is replaced or removed. Reuse existing correction snapshots where they contain the required evidence. For transitions that currently overwrite or delete the only record, add the missing history in the same transaction as the ledger write, using the same member lock and stable source or request ID for retries. For older strikes, show the cycle date and any supported timestamp, or **Issuance time unavailable**. Legacy totals and dry-run candidates provide no history entries by themselves.
5. **Refresh after changes.** Reload the selected month's history after a Metastrike replacement or a staff correction and when the member reopens the calendar. Check that counted entries agree with the punishment ledger for the same local-cycle month. Give the strike section clear empty and retry states so a history-read failure leaves sleep details usable.

## 4. Replace instant Metastrikes with dated requests

The current [Metastrike route](src/app/api/members/strikes/metastrike/route.ts) applies a pass immediately, substitutes a reason when the member leaves it blank, and charges the month in which the pass is applied. The requested workflow requires approval for each dated pass. Build it on the active, verified punishment ledger after the production recovery.

### Request submission

- Start with **the previous three sleep-cycle dates, the current cycle, and the next three dates**. This gives members a few days to submit a missed-night request and a few days to plan ahead, with at most seven choices. Use a short date list in [MetastrikeModal.tsx](src/components/MetastrikeModal.tsx), default to the current cycle when eligible, and label the dates in the member's effective timezone. Base the window on the existing Luxon sleep-cycle anchor, so a bedtime just after midnight remains attached to the correct night. Past choices require an existing nightly strike. Grey out cycles with an approved pass or an outstanding request, and show why a date is unavailable. Use the separate dated correction workflow for staff-added strikes with no nightly source.
- Require a reason of 1–500 characters after trimming. Reject missing, empty or whitespace-only reasons on the server and give inline feedback in the form. Require an explicit cycle date and reuse a request ID on retry. Use the linked member's active session to resolve ownership and validate the date, source and quota server-side. Store the selected cycle date, reason, submission timestamp, applicable timezone and source strike ID if present. Once accepted, a request stays reviewable after the submission window closes.
- Keep the limit at **three passes per target sleep-cycle month**. An outstanding request reserves one slot in that month. Approval consumes it once, and rejection or withdrawal frees it. Show used, reserved and remaining slots for the selected month. A pending request neither protects an upcoming night nor removes a recorded strike. Tell the member that approval is required and that a regular strike can still be recorded before review. Preserve the existing balances and accounting for passes already applied before this release.

### Moderator review and decisions

- Add a **Metastrikes** section in [ModDrawer.tsx](src/components/ModDrawer.tsx) with a pending count, oldest-first requests and recent decisions. Each request shows the member, selected night, reason, submission time, existing strike or protection status for that cycle, and quota. Offer **Approve** and **Decline** with confirmation and a short member-visible explanation on decline. Keep requests, decisions and reasons in the relevant member and staff views. The member can see pending, approved, declined, withdrawn or closed without use in their request history and withdraw a pending request.
- Add staff-only queue and decision routes under `/api/mod/metastrikes`. Reuse live Discord role checks and target locks. Moderators review members, and the Owner reviews members and moderators. Staff cannot approve their own requests. Resolve the Owner's review path with the same explicit, audited operator policy proposed for Owner punishments before accepting an Owner request. Keep the reviewer and decision time in the audit. Use same-origin mutations, stable request IDs and a compare-and-update on the pending state so two reviewers or a retry cannot apply a pass twice.
- **Approval before the strike cutoff** protects only the selected cycle. **Approval after a strike is recorded** replaces the regular strike for that cycle with a Metastrike, even if the next bedtime or month boundary has passed since the member submitted the request. If the dispatcher is still settling the cycle, keep the request pending until the strike or a protected outcome is known. If a check-in or dated correction means the cycle already has no strike to excuse, close the request without charging a pass and record why. Recheck the recorded source at approval so a stale decision cannot replace an unrelated strike.
- Apply the decision, nightly write, pass charge and punishment reconciliation in one transaction under the existing rollout/member lock order. Store the charged month explicitly for new passes and reuse it on a later audited reversal. Reconcile the **month of the selected cycle**, refresh the member's current projection, and preserve the original strike and review result in the My Sleep history. Cancel any open threshold the strike no longer supports, refresh progress toward 3, 6, 9 and onward, and retain completed tasks in history. Surface the updated status and counts in My Sleep and the moderator queue.
- Keep an earned task pending for assignment while an eligible strike can still be submitted for replacement and that replacement could invalidate the threshold. An accepted pending request extends the hold until a decision or withdrawal. Recheck on assignment and completion under the same lock. If an already-assigned task is affected during rollout, pause completion while the request is pending. Resume it with its saved details if the request is declined, or cancel it if approval invalidates the threshold. Use existing threshold math so an unrelated request does not block a task.

### Release changes

- Add durable request records and a monthly read for the member. Switch the modal and all roster and calendar CTAs to **Request Metastrike**, retire the legacy immediate-apply and conversion actions at cutover, and close any compatibility path that bypasses review. Keep legitimate staff balance corrections audited and consistent with reserved slots and approved passes. Adjust the dispatcher's protection check, the punishment assignment deadline, and the My Sleep history to read the approved state. Update the product, backend and design specs to describe the reviewed workflow, replacing the old next-bedtime conversion rules.
